      Let's set up your first certificate authority
      
              
      Akamana issues the certificates that let your servers prove who they
                are over HTTPS and SSH. Before issuing anything you build a small chain of trust.
      
              
        
                
      1. 1Root certificate. Your trust anchor.
                  Every device that should trust your certificates gets this one file added to its trust
                  store. Keep its private key very safe.
        2. 
                
      2. 2Intermediate certificate. The root
                  signs an intermediate, and the intermediate signs your day-to-day service certificates
                  — so the root's key can stay locked away.
        3. 
                
      3. 3Service certificates. What you put on
                  each website, API or load balancer. Signed by the intermediate, so anything trusting
                  your root trusts them too.
        4.

          Auto-renew

                          expires and pushes it to every target below.
          
                      
          
                      
                    
          
                    
          
                    
                  
          
                
          
              
          
            
          
          
          

          
          
          
            
          An SSH certificate is a public key signed by a CA, carrying
              its principals, an expiry and a serial. Unlike a plain key you must copy into every server's
              authorized_keys, a certificate is trusted anywhere the CA is trusted — so
              you distribute the CA key once and then issue short-lived certificates centrally, with real
              expiry and revocation.
          

            
          
              
          
                
          User CA — proves who a user is
          
                
          
                  
          Principals are the usernames the certificate may log in as. On each
                    server, trust the User CA in sshd_config.
          
                  
          TrustedUserCAKeys /etc/ssh/akamana_user_ca.pub
          
                
          
              
          
              
          
                
          Host CA — proves a server's identity
          
                
          
                  
          Principals are the hostnames. On clients, add a
                    @cert-authority line to known_hosts.
          
                  
          @cert-authority *.example.com ssh-ed25519 AAAAC3Nza…

          Backup & restore
          
                
          Encrypted database exports, kept under /data/backups and
                  rotated. Keep the passphrase safe — it is required to restore on another machine.
          
                
          A database backup alone is not enough to rebuild an instance: keep
                  KEY_ENCRYPTION_KEY_B64 and JWT_SECRET safe. Encrypted private
                  keys are unrecoverable without the key-encryption key.
          

                
          
                  
          
                    Automatic backups

                    Encryption mode
                    
          
                      
                      
                      
                    
          
                  
          
                  
          
                    
                    
                  
          
                  
          
                  
          
                    
          Envelope mode uses a random key per backup, encrypted for each
                      recipient's RSA public key. Any one recipient can restore with their private key
                      — the server never holds a decryption key.

          Credentials
          
              
          Secrets Akamana uses to connect to hosts. Secret material is encrypted
                at rest and is never shown again after saving.

            public half is in the target's authorized_keys. An SSH password is
            simpler but less secure. An API token is for hosts you manage through an API.
            The account needs permission to write the certificate files and run the reload command.
