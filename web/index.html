      Welcome — let's set up your first certificate authority
      
            
      CryptoKeyMancer issues the certificates that let your servers prove who they are over HTTPS and SSH. Before issuing anything, you build a small chain of trust:
      
            
        
              
      1. Root certificate (Root CA). This is your trust anchor. Every device that should trust your certificates must have this one file added to its list of trusted authorities (its "trust store"). You install it once per machine. Keep its private key very safe — anyone who has it can impersonate your services.
        2. 
              
      2. Intermediate certificate. The root signs an intermediate, and the intermediate is what actually signs your day-to-day service certificates. Why the extra layer? So the root's key can stay locked away: if an intermediate is ever compromised you replace just the intermediate, not the root you painstakingly distributed everywhere.
        3. 
              
      3. Service (leaf) certificates. These are the certificates you put on each website, API, or load balancer. They are signed by the intermediate, so any device that trusts your root automatically trusts them too.
        4. 
            
      
            
      What about the files? A service needs two pieces: the certificate (public, shareable — usually a .crt/.pem file, often combined with the intermediate into a "full chain") and the private key (secret — a .key file, never shared). Windows often bundles both into a .pfx. SSH uses a key pair instead of a certificate; PuTTY on Windows wants that key in .ppk format.
      
            
      Click below to create your Root CA. CryptoKeyMancer will recommend safe defaults at every step and explain each choice.

          An SSH certificate is a public key that has been signed by a Certificate Authority (CA), with extra fields baked in: which principals it is valid for, an expiry date, a serial, and options. Unlike a plain SSH key (which you must copy into every server's authorized_keys), a certificate is trusted anywhere the CA is trusted — so you distribute the CA public key once and then issue short-lived certs centrally, with real expiry and revocation.
          
              
          There are two kinds, each signed by its own CA:
          
              
            
                
          1. User certificate — proves who a user is. Principals are the usernames the cert may log in as. On each server, trust the User CA by adding TrustedUserCAKeys /etc/ssh/ezkey_user_ca.pub to sshd_config. The user logs in with their id_ed25519 + id_ed25519-cert.pub.
            2. 
                
          2. Host certificate — proves a server's identity (kills the "unknown host key, continue?" prompt). Principals are the hostnames. On clients, trust the Host CA with a @cert-authority *.example.com ssh-ed25519 … line in known_hosts; on the server set HostCertificate /etc/ssh/ssh_host_ed25519_key-cert.pub.
            3.

          API Tokens
          
          
          
            
          An API token lets a script, CI job, or deployment tool authenticate to CryptoKeyMancer's programmatic API instead of logging in with a username and password. Send it as a bearer header: Authorization: Bearer ezk_….
          
            
          Least privilege: a token only carries the scopes you tick below — nothing else. A git-deployment token that just needs to request certificates should get only tls:issue and/or ssh:sign, never user or delete rights. You can only grant scopes your own role already has.
          
            
          Shown once: the full token value is displayed a single time when created and is never recoverable — store it in your secret manager immediately. You can always revoke a token and mint a new one. See the Developer API page for usage examples.

          Credentials
          
          
          Secrets CryptoKeyMancer uses to connect to hosts (SSH keys/passwords, API tokens). Secret material is encrypted at rest and is never shown again after saving.
          
          
          
            
          Which kind to choose: an SSH key is recommended — paste the private key whose matching public key is in the target's authorized_keys. An SSH password is simpler but less secure. An API token is for hosts you manage through an API rather than SSH.
          
            
          CryptoKeyMancer only stores the encrypted secret; you can update it later but never read it back. The account you use needs permission to write the certificate files and run the reload command on the target.

          Create Organization and Root CA
          
        
          A Root CA is the trust anchor. It should remain highly protected.
          
        
          
          
          Validity (years): a root is distributed to every device once and rarely changes, so it lives a long time — 10 years is a good default. Re-distributing a new root to every machine is painful, so don't make it too short.
          
          
          Key type: Ed25519 is recommended — small, fast, and very strong. Choose RSA 4096 instead only if some old device or appliance can't understand Ed25519 (maximum compatibility, larger/slower keys). ECDSA P-256/P-384 is a middle ground.
          
          
          Create an intermediate now (recommended): the intermediate does the everyday signing so the root can stay offline/protected. Leave this on unless you have a specific reason not to.

          Import an existing Root CA
          
        
          
          
          Paste an existing Root CA certificate to register it in CryptoKeyMancer. Include its private key if you want CryptoKeyMancer to issue intermediates and certificates under this root. Without the private key the root is registered as a trust anchor only — you can publish and distribute it, but not sign new certificates with it.
          
          
          Key type and validity are read automatically from the certificate.
          
        
          
        
          
          
          
        
          
        
          
          
          
        
          
        
          
          
          
        
          
        
          
          
          
        
          
        
          
          
        
      
          
      
          
              

    
      
          
        
          Create certificate
          
        
          
          
          Leaf vs intermediate: pick Leaf certificate for an actual service (a website, API, load balancer). Pick Intermediate CA only if you are building another signing layer.
          
          
          Validity (days): shorter is safer because a leaked certificate stops being valid sooner. 365 days is a sensible default for internal services; enable auto-renew so you never have to remember.
          
          
          Key type: Ed25519 is recommended for speed and strength. Use RSA 2048/4096 if a client is old or you need broad compatibility (e.g. some Java or appliance stacks). The certificate is the public half (.crt/.pem); the private key (.key) stays on the server and is never shared.
          
        
          
        
          
          
          An SSH key is just a key pair — there is no CA, hierarchy, or hostname. Give it a comment (usually the user it is for), pick the algorithm (Ed25519 recommended), and a validity. Install the public key in the target's authorized_keys; keep the private key secret (PuTTY on Windows uses .ppk).
